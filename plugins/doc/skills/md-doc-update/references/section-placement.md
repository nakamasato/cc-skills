# 新しい節をどこに置き、どう名付けるか

`md-doc-update` で内容を足すときの配置・命名の判断基準。
見出しの語形・器語の禁止・粒度・定訳・実在 doc のコーパスは
`md-doc-refactor` 側と共有する（重複させない）:

- `../../md-doc-refactor/references/heading-forms.md`
- `../../md-doc-refactor/references/section-vocabulary.md`
- `../../md-doc-refactor/references/ja-heading-glossary.md`
- `../../md-doc-refactor/references/corpus.md`（実在 117 件の逐語見出し）

---

## 手順

### 1. 足す前に「既存のどの節の中身か」を疑う

新しい節を作るのは**最後の手段**。まず次を確認する。

- 既存の H2 のどれかの配下（H3）に収まらないか
- 既存の節の一項目として本文に足せないか
- そもそもこの doc の担当範囲か。別 doc に属するなら、そちらに書いてリンクする

**仲間のうちの 1 つを H2 に昇格させない。** 昇格候補を外したとき、残りの
兄弟が同じ器の名前で説明できるなら、それは章ではなく中身
（`heading-forms.md` §7）。

### 2. doc の種別を決め、正規スロットのどれかを言う

README / getting-started / configuration / troubleshooting / ADR /
SECURITY / CONTRIBUTING / migration / api-reference / FAQ / runbook。
種別ごとの標準列は `section-vocabulary.md`。

新しい節が**どのスロットにも当たらない**なら、それは名前が悪いのではなく
その doc に属していない。

### 3. 置く位置

読者の動線の順に並べる。既定の並びは

```
Scope / 概要 → 仕組み・概念 → セットアップ・手順 → 既知の落とし穴
→ Troubleshooting → Related / 次のステップ
```

- 概念は手順より前。手順の途中に概念を割り込ませない
- 事故・禁止事項は落とし穴に吸収。独立章にしない
- 締めの節（`Related` / `次のステップ` / `See also`）は 1 つだけ、必ず最後
- **環境・platform 別の内容を新しい H2 にしない。** 親手順配下の H3 にし、
  動作の違いは仕組みへ、事故は落とし穴へ分配する（`heading-forms.md` §6）

### 4. 名前を付ける

- **既定は名詞句。** 断定文・口語・「〜する」を手順以外に使わない
- 手順の節・ステップだけ動詞終止形または番号プレフィックスを許す。
  兄弟の中で語形を揃える
- **器の名前を使わない**: `基本の〜` `〜について` `〜まわり` `〜こと`
  `その他` `Tips` `ポイント`。器語は最終節の残余受けのときだけ
- 日本語の語は `ja-heading-glossary.md` の attested 語から選ぶ。訳語を発明しない
- 主張は見出しではなく**本文の 1 行目**に置く

### 5. 足したあとの兄弟テスト

追加した節の**兄弟を並べて読む**。

- [ ] 語形が揃っている（全部名詞句、または全部手順動詞）
- [ ] 全部が同じ問いの答えになっている
- [ ] 1 つだけ抽象度が高い / 低いものがない
- [ ] 追加によって既存の節が器化していない（中身が減って名前だけ広くなった）
- [ ] 締めの節が 2 つになっていない

浮いているものは、たいてい別の H2 の配下に属する。

## やってはいけないこと

- 一般テンプレ（`概念 → 設定 → 運用 → トラブル`）を中身を見ずに当てる。
  本文を段落単位で棚卸しし、読者の問いで束ねてから名前を選ぶ
  （`heading-forms.md` §8）
- 経緯・時系列を節にする（`これまでに踏んだこと`）。doc は最新仕様の
  スナップショット。過去の事故を残すなら日付つき固有名で末尾に置く
- 追記だけで終える。節を足したら、その内容を持っていた既存の記述を
  必ず引き上げるか参照に置き換える
